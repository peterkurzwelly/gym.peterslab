# Decisions and assumptions

Where the build deviates from or interprets SPEC.md / PROGRAM.md. Peter: skim this and push back on anything that is wrong.

| # | Decision | Why |
|---|---|---|
| D1 | One Worker (`gym`) serves the PWA as static assets and the API under `/api`, instead of Pages + a separate Worker. | Matches the peterslab.app convention (one repo and Worker per app on `slug.peterslab.app`). One deploy, one domain. |
| D2 | Program templates (program, phase, program_day, prescription) live in `config/program.json`, not in database tables. User edits (block swaps, session order) live in the synced `settings` row. | Templates are static; storing them as rows would drift from config. Logs keep target and actual side by side, so history is intact. |
| D3 | `training_week` stores only user flags (`repaired`). Week state (done counts, floor, target, zero, training week index) is always computed by the engine. `progression_state` is computed, not stored. | Derived data stored in synced rows goes stale and conflicts. The engine replays history deterministically, so it is always right and changing `engine.json` changes behavior immediately (acceptance criterion 6). |
| D4 | Check-in scores: 1 to 5, higher is better for all four (soreness 5 = fresh, stress 5 = calm). | One direction makes the average meaningful and the UI consistent. |
| D5 | Progression is tracked per exercise + rep range ("track"); e1RM stats per exercise. | Romanian deadlift appears light (8 to 10) and heavy (6 to 8); one load track would mix them. |
| D6 | Face pull 12 to 15 (program: 2 × 15), biceps curl and triceps pushdown 10 to 12 (program: 2 × 12). | Double progression needs a range; a single number makes every 14 a "below range". |
| D7 | Large jump: every set ≥ top + 1 and at least half the sets ≥ top + 2. | SPEC 6.3 maps 10, 10, 9 (range 6 to 8) to the larger jump, while PROGRAM.md says all sets beat by 2+. The spec example is an acceptance test, so this rule satisfies both as closely as possible. |
| D8 | Reactive deload makes the *next* training week the deload and cancels week 8. After week 8 it only flags. | "Pulls the week 8 deload forward (once per block)". |
| D9 | Repair = streak freeze: a repaired zero week keeps the run going and counts in "weeks without a zero", but the phase still does not advance. | Spec says one repair per 4 weeks without defining it. |
| D10 | A zero week is a completed week with no strength, travel or cardio session. Walks do not count. | "Weeks without a zero" and "floor weeks" are shown separately, so zero ≠ below floor. |
| D11 | Never miss twice: nudge when 48 h have passed since the last strength session and the floor is not reached. | SPEC 6.4 wording. There are no planned days to miss. |
| D12 | Readiness load cut applies to the first exercise (PROGRAM.md "take 5 to 10% off the first exercise"); configurable. | SPEC says "top set"; the program is more specific. |
| D13 | Rest timer alert: sound + screen flash. iPhone Safari has no vibration API. | Platform limit. |
| D14 | Sync auth: a sync key (Worker secret `SYNC_TOKEN`) pasted once in Settings on each device. Cloudflare Access JWT verification is also implemented and switches on when `ACCESS_TEAM_DOMAIN` and `ACCESS_AUD` are set. `/api` refuses everything when neither is configured, except the public `GET/HEAD` routes `/api/health`, `/api/auth/login` and `/api/ics` (the calendar link opens outside the app without the key; it echoes its query and reads no stored data). The app shell is public and holds no data. | Peter chose the sync key on 2026-11-08: home screen apps on iPhone can loop on Access login when the session expires. The repo and subdomain are public, so the API fails closed. Logging never depends on the network. |
| D15 | D1 database in the EU jurisdiction. | Personal training and check-in data. |
| D16 | Pull-up is the default B3 exercise (spec order); lat pulldown is one tap away and can be swapped for the block. | Spec order. Swap if pull-ups at bodyweight are too hard for week 1. |
| D17 | Defaults from Peter's answers (2026-11-08): no limitations, intervals on bike or rower (both offered), week killers = work peaks, travel, evenings. The app leads with the ★ 30 min version after the evening hour (default 19:00) and when the floor is at risk, keeps the travel version one tap away, and pushes the Sunday booking of two floor sessions. | SPEC 11.4 and 11.5. |
| D18 | Sessions dated in the 7 days before the Monday of `block_start_date` count toward week 1: strength and cardio counts, floor, target, zero week, the week card and Plan, volume and walking minutes. They progress as training week 1 of the return phase. Before the block starts, Today offers Session A as week 1. | Peter is likely to start early (the block starts Monday 2026-11-09). A session the day before should count, not vanish. |
| D19 | Never miss twice measures its 48 h from the latest of the last strength session, this week's Monday 00:00 and block start (refines D11). | Without the week bound a normal weekend gap after a perfect week turned the nudge on nearly every Monday and led with the ★ 30 min version although nothing was missed. |
| D20 | A session that is both the short version and a comeback takes the larger of the two set reductions, not both. | Both together gave single sets on three exercises. The Monday after a zero week no longer triggers never miss twice (D19), so the full version, which is the comeback plan, leads. |
| D21 | Reactive deload "missed reps" only counts below range exposures with added load on double progression tracks. A double progression track below range twice at bodyweight holds at rep_min and names an easier alternative (`dp.bodyweight_hold`) instead of "reset to 0 kg". | Pull-ups and knee raises below range in the return phase are about the variation, not fatigue. They pulled a deload into week 3 and cancelled the week 8 deload. |
| D22 | The consolidate top set is at least one step above today's work weight. | The latest e1RM can lag the work target, which gave a top set at RIR 1 at the weight just prescribed for more reps at RIR 2. |
| D23 | Volume flags skip zero weeks and only fire where a week is outside the band and further from it than the program as written. | The program itself is outside 8 to 10 on several muscles, so every target week raised six flags Peter could not act on, and a zero week listed "0 sets" for every muscle. Swaps, short versions and missing sessions that move volume out of the band still flag. |
| D24 | `extension_weeks` is the current calendar week index minus the current training week: zero weeks plus weeks a long break restart took back. | The UI shows it as "Block runs N weeks longer", which left out restarts. |
| D25 | The readiness banner states what actually changed: the real loads ("Back squat 65 → 60 kg") and the sets actually dropped after the minimum. Personal bests come only from progression eligible sessions and leave out bodyweight exercises. A session's cardio minutes count in the session's week. | Rounding down made "−5%" a 7.7% cut, the min_sets clamp made "1 set dropped" untrue on short days, hold sessions repeated PRs, and cardio saved after midnight split across two weeks. |
| D26 | Body and fuel is its own engine call (`computeBody`) on a new synced table `body_log` (one row per local date). The maintenance estimate is Mifflin St Jeor × an activity factor per job (desk 1.4, feet 1.6, physical 1.8, the program's training included) and is only a starting point: a weekly adjustment of 100 kcal, at most 400 either way, corrects it from the real weight trend. The adjustment is replayed from the logs with the *current* goal and cut rate, so changing either re-reads past weeks. It skips weeks with fewer than 3 weigh-ins (that week or the one before) or protein logged on fewer than 4 days. Recomp is "hold weight" at −100 kcal; gain aims at 0.25% a week and at most 0.5%. The calorie target never goes below 1500 kcal (male) or 1200 kcal (female) unless Peter sets his own number. All of it lives in `config.body` and is coaching convention, not research. | The goal is to get lean, and the app only covered lifting. A formula alone is off by a few hundred kcal for many people, so the trend has the last word. Thin data should never move the target, and nothing here stores derived numbers (D3): targets and adjustments are computed from logs and settings every time. Settings do not keep a history of the goal, so a replay cannot know what the goal was in an earlier week. |
| D27 | The UI was rebuilt on 2026-11-12 around the goal "get lean and strong", not "keep a log". Four tabs: Today, Program, Progress, You. A workout runs full screen, one exercise at a time, with one primary button ("Log set 2 · 60 kg × 8"). The design is "night + volt": near black, white text, one volt accent for actions and done, three data colors (protein coral, steps and cardio blue, body weight violet), Barlow Condensed for headings and numbers, the system font for everything else. This replaces the ink, paper, orange, Instrument Serif and IBM Plex Mono design of SPEC 5. SPEC 9.1 (first set within 2 taps of a cold open) is now 3 taps: Start workout on Today, Start workout on the overview, then the log button. The overview stays because it is where the exercises, their guides, the version and swaps are checked before the clock starts. | Peter's feedback on v1: wrong direction, design and colors disliked, exercises were only names. |
| D28 | Every exercise has a guide: start and end photo (free-exercise-db, Unlicense, self hosted and precached), a plain how-to (what it is, what to look for in the gym, set up, do it, where you feel it, what to avoid) and one YouTube video checked through oEmbed. The video plays in a youtube-nocookie.com frame only after a tap; CSP allows that one frame source. Content lives in `data/exercise-guides.json` and is checked by `npm run data:validate`. | "I don't understand some of the exercises, they are just names." A guide that needs signal is useless in a gym basement, so text and photos work offline and only the video needs a connection. |
| D29 | The screen never shows gym shorthand. The engine keeps its own wording (and its tests); `apps/web/src/lib/plain.ts` rewrites RIR, floor, e1RM and deload for display, and `lib/effort.ts` words effort targets as "leave 3 in the tank". Stored decisions keep the engine's text. | Plain words without touching 500 engine tests or the audit trail. If the engine's own copy is ever rewritten, delete plain.ts. |
| D30 | QA of the body engine (2026-11-12) changed three rules. (1) A changed goal or pace never re-judges past weeks: `settings.body_adjust_since` and `settings.body_adjust_base_kcal` (migration 0005) carry the correction earned so far and restart the weekly judgement from the first Monday on or after the change. (2) The weekly change and the trend rate are scaled by the real number of days between the weigh-ins behind the two averages, with `adjustment.min_gap_days` as the lower bound. (3) An override of 0 counts as not set. The screens show the engine's `current_weight`. | Replaying every week against the current goal turned eight on-plan weeks into "plus 400" or the calorie floor the moment the pace was changed. Comparing a week weighed Thursday to Sunday with a full week read an on-pace start as "100 kcal less". Known and left: a correction earned before a pause of many weeks stays until new weeks move it, and `body_log` is last write wins per day, so two devices that both log the same day before syncing keep only the later row. |
| D31 | One open session at a time, enforced by the screens (QA 2026-11-12). Cardio says "Your workout is still open" and leads back to it; Workout says "Cardio is running" and leads back to that. The player holds the session it played while the live engine state lags the first set or runs ahead of finish, and stops taking sets when that session was finished or discarded elsewhere. Pain flagged before an exercise's first set is kept on the device (`gym.workout.pain`) until finish or discard. | The engine treats the newest open session as the active one, so a second open session hid the first until it was saved. Live queries are asynchronous: without the hold, leaving after the first set landed on the overview and finishing flashed "Done for today". |
